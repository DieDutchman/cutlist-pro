#### Overall Impression

The engineering discipline underneath this app is genuinely above-average for a single-file app — the custom `confirmAction`/`showToast`/focus-trap system replacing native `alert`/`confirm`/`prompt` uniformly, with `aria-live` wiring and focus restoration, is not what a "vibe-coded" app looks like. But that discipline is unevenly applied across the file's history: newer surfaces (scenario compare) get full dialog semantics; older-but-still-live modals (feedback, plan-import, quote manager) don't. The single biggest opportunity is closing that gap once, systematically, rather than continuing to hand-roll each new modal/tooltip/icon choice independently — the icon-vocabulary split and tooltip-mechanism split are the same underlying problem (no single enforced component) wearing two different costumes.

#### What's Working

1. **Custom dialog/toast/prompt system with real accessibility engineering** (`dev.html:5088-5296`) — focus restoration to the triggering element, `aria-live` wiring, fail-closed confirmation timeouts. This is above what most single-file apps bother with.
2. **Rigorous token discipline in the base CSS** — amber restraint (≤15% rule holds), Mono-for-every-number, flat-by-default shadows, ≤6px radius — sampled across `dev.html:11-1646` with zero violations of DESIGN.md's explicit bans.
3. **The newest accessibility work is genuinely good when it's applied** — the scenario-compare modal (`dev.html:11852`) has `role="dialog"`, `aria-modal`, auto-focus, Escape handling, and a reused focus-trap helper. Proof the team knows how to do this right; the gap is coverage, not knowledge.

#### Priority Issues

**[P1] Modal accessibility markup is inconsistently applied across 13 modals**
- **Why it matters:** Screen-reader users (Sam) get a fully different, worse experience depending on which dialog happens to be newer. `feedback-modal` (`4863`), `plan-import-modal` (`4924`), `bulk-adjust-modal` (`4937`), `import-prices-modal` (`4979`), `board-cleanup-modal` (`5059`), `hist-price-modal` (`27862`), and `qm-modal` (`4808`) have none of `role="dialog"`/`aria-modal`/`aria-label`, while `users-modal` (`4654`), scenario-compare (`11852`), Import Unit (`16977`), Edit Unit Parts (`17877`), and Keyboard Shortcuts (`30804`) do.
- **Fix:** Extract the scenario-compare modal's dialog scaffolding (role, aria-modal, focus trap, Escape handler) into one shared helper and retrofit the 7 modals missing it.
- **Suggested command:** `/impeccable harden`

**[P1] Destructive-delete confirmation lives in a non-blocking corner toast, not a modal**
- **Why it matters:** `confirmAction()` (`5206-5225`) has good copy ("This cannot be undone") and a safe fail-closed default, but the surface itself — a dismissable toast — is easy to miss or click past given the user's attention is elsewhere. For an app whose stated differentiator is trust through "the numbers are right" and "no surprises," the confirmation UI for irreversible actions should feel at least as serious as the informational modals already do.
- **Fix:** Route `confirmAction()` through the same blocking-modal scaffolding recommended for the fix above, at least for genuinely destructive/irreversible actions (job delete, archive, CLEAR ALL).
- **Suggested command:** `/impeccable harden`

**[P2] Two competing tooltip mechanisms coexist**
- **Why it matters:** A purpose-built `[data-tip]` CSS component (`627-654`, theme-aware, keyboard-focusable) exists but is used only 5 times, against 194 native `title=""` attributes — including the entire P&L Hardware table's variance-explanation cells. Native tooltips don't fire on touch, don't match the app's visual system, and aren't keyboard-accessible the same way.
- **Fix:** Migrate high-value `title=` usages (anything explaining a number or a variance, not just decorative hints) to `[data-tip]`.
- **Suggested command:** `/impeccable clarify`

**[P2] Icon vocabulary is split between full-color emoji and monochrome glyphs on structurally identical tab buttons**
- **Why it matters:** Room tabs (🍳🛏🚪🚿) and tool tabs (✦▦✏☰) sit in the same row with no shared visual system, undercutting the "precise, efficient, professional" brand personality. This is the clearest AI-slop-adjacent tell in the file per Assessment A — not because emoji are inherently wrong, but because the inconsistency reads as unplanned drift rather than a deliberate choice.
- **Fix:** Pick one lane — either all room/tool tabs get themed monochrome glyphs (matching the "instrument, not consumer app" brand), or commit to emoji everywhere with a documented rule for which ones. Either is defensible; the split isn't.
- **Suggested command:** `/impeccable typeset`

**[P2] The new P&L "suggest a match" feature has no discoverability signal**
- **Why it matters:** Nothing on the P&L tab tells the user "3 hardware lines have possible matches waiting" — the only way to find a suggestion is to scroll the Hardware table row by row and notice an italic sub-row. For a feature specifically about reconciling real invoiced cost against quoted cost, passive discoverability undersells its own value. Relatedly (raised as a provocative question below): the feature already computes a real similarity score (`_plMatchScore`) but throws it away in the UI — showing "82% match" vs. "51% match" would materially change how much a user should trust a one-click Link.
- **Fix:** Add a count badge (e.g. on the HARDWARE section header, or the P&L tab itself) showing how many lines have pending suggestions, and consider surfacing the match score/confidence next to the suggestion text.
- **Suggested command:** `/impeccable clarify`
